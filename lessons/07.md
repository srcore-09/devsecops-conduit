# Lesson 07 · Docker: build the application once, run the same box everywhere

By the end of the lesson:

- Docker runs on your server;
- the API and the frontend run as containers instead of your hand-made services;
- the robot builds and publishes both images for every commit;
- you switched between two versions in seconds.

You work on the laptop, in `~/devsecops-conduit`, and on your server, where the complete Conduit runs at `https://YOUR-NAME` since Lesson 4. In the commands, replace `YOUR-IP` with the address of your server and `<you>` with your GitHub username **in lower case**.

## Starting state

- `https://YOUR-NAME` shows your Conduit, and the services `conduit` and `conduit-web` run on the server (Lesson 4).
- Your fork has `deploy/` (Lesson 5) and a `deploy` job in `.github/workflows/ci.yml` (Lesson 6).

## Mission 1 · Docker on the server (15 minutes)

**1. Install Docker:**

```bash
ssh azureuser@YOUR-IP
sudo apt update
sudo apt install -y docker.io
sudo docker run --rm hello-world
```

Checkpoint: a message that starts with `Hello from Docker!`.

**2. Give the small server some room.** Your server has 1 GB of memory and no swap. Building an image while the site keeps running can use more than that, and then the server freezes until somebody restarts it in Azure. A swap file lets the kernel move what is not used right now to the disk:

```bash
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo "/swapfile none swap sw 0 0" | sudo tee -a /etc/fstab
free -m
```

Checkpoint: the line `Swap:` shows about `2047` in the first column.

> [!NOTE]
> Memory is fast and small, the disk is slow and large. Swap is a part of the disk that the kernel may use as overflow when memory is full. It is slow, so a busy server should not live in it, but it turns “the server froze” into “the build was a bit slower”. The last line makes it permanent after a reboot.

**3. Visit a box that is not your server:**

```bash
sudo docker run --rm -it ubuntu:24.04 bash
```

Inside, run `hostname`, `ls /home` and `ps aux`. Different name, no `azureuser`, only two processes. Leave with `exit`: the box is gone.

> [!NOTE]
> Your server is a virtual machine with its own operating system. A container is only a fenced area inside it: its own files, its own processes, its own network name, but the same kernel as the server. That is why it starts in a second and weighs megabytes, not gigabytes.

> [!WARNING]
> Whoever can talk to Docker can start a box that sees the whole server as `root`. Adding yourself to the `docker` group would make that permanent and invisible. Typing `sudo` keeps it a conscious choice.

## Mission 2 · The API in a box (40 minutes)

**1. A branch on the laptop:**

```bash
cd ~/devsecops-conduit
git switch main
git pull
git switch -c docker/images
```

**2. Read `backend/Dockerfile` with the instructor.** It has two stages. The first one compiles the libraries. The second one takes only the result, adds a small user `app`, copies the code and starts the API. Then change its end so it reads:

```dockerfile
RUN chmod +x /app/scripts/docker-entrypoint.sh
USER app

ARG APP_REVISION=dev
ENV APP_REVISION=$APP_REVISION
ENV UVICORN_HOST=0.0.0.0
ENV UVICORN_PORT=8000
EXPOSE 8000

HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
    CMD curl -f http://127.0.0.1:${UVICORN_PORT}/api/health-check || exit 1

ENTRYPOINT ["/app/scripts/docker-entrypoint.sh"]
CMD ["uvicorn", "conduit.app:app"]
```

Four things changed:

- the code is no longer handed to `app` (`chown` is gone): as in Lesson 3, the program may read its code but not change it;
- the commit SHA goes into the image as `APP_REVISION`;
- the address and port come from `UVICORN_HOST` and `UVICORN_PORT`, so the same image can listen wherever the server needs it;
- the port is `8000`, the one Caddy and the frontend already use.

Add one line to `backend/.dockerignore`, so your local Python environment never goes into the box:

```text
.venv
```

```bash
git add backend/Dockerfile backend/.dockerignore
git commit -m "Run the API from a Docker image"
git push -u origin docker/images
```

**3. Build the image on the server**, from your branch:

```bash
cd /opt/conduit/src
sudo git fetch
sudo git switch docker/images
sudo docker build -t conduit-api:local --build-arg APP_REVISION=local backend
```

The first build takes a few minutes. While it runs, watch the steps: every line of the Dockerfile is one step.

Build it again right away:

```bash
sudo docker build -t conduit-api:local --build-arg APP_REVISION=local backend
```

It takes seconds: every step comes from the cache.

> [!NOTE]
> An image is a stack of layers, one per line of the Dockerfile. Docker keeps every layer and reuses it until something above it changes. That is why the libraries are installed before the code is copied: code changes every day, libraries rarely.

**4. Replace the service with a container.** Stop the hand-made service and start the box in its place:

```bash
sudo systemctl disable --now conduit
sudo docker run -d --name conduit-api \
  --network host \
  --env-file /etc/conduit/conduit.env \
  -e UVICORN_HOST=127.0.0.1 \
  --restart unless-stopped \
  conduit-api:local
```

`--network host` lets the box use the server's network, so the API is again at `127.0.0.1:8000` and reaches PostgreSQL at `127.0.0.1:5432`. `--env-file` hands it the same locked secrets as before. `--restart unless-stopped` does what systemd did: start it again after a crash and after a reboot.

**5. Check it:**

```bash
sudo docker ps
curl -s localhost:8000/api/health-check
sudo docker exec conduit-api whoami
sudo docker exec conduit-api touch /app/hacked
```

Checkpoint: the container is `Up`, the health check ends with `"revision":"local"`, the user is `app`, and `touch` says `Permission denied`. Open `https://YOUR-NAME`: the site works. The frontend still runs the old way and now talks to an API in a box.

## Mission 3 · The frontend in a box (55 minutes)

**1. Write the frontend's Dockerfile.** Replace `frontend/Dockerfile` with:

```dockerfile
FROM node:22-slim AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:22-slim
WORKDIR /app
ENV NODE_ENV=production
COPY package.json package-lock.json ./
RUN npm ci --omit=dev
COPY --from=build /app/build ./build
COPY server.js ./
USER node
EXPOSE 3000
CMD ["node", "server.js"]
```

The first stage installs every library and builds. The second starts again from a clean Node, installs only the libraries the running server needs, and copies the result of the build.

**2. Pin every version with a lock file.** `npm ci` refuses to work without one. You do not need Node on the laptop: a box with Node makes the file for you.

```bash
docker run --rm -v "$PWD/frontend:/app" -w /app node:22-slim npm install --package-lock-only
git add frontend/Dockerfile frontend/package-lock.json
git commit -m "Run the frontend from a Docker image"
git push
```

> [!NOTE]
> `package.json` says “React Router 7.9 or newer”. The lock file says “exactly 7.18.4, with exactly these 500 other packages”. Without it, every install takes whatever is newest that day. That is how a server in Lesson 4 got a different React Router than the instructor's laptop and broke the sign-up.

**3. Build and run it on the server:**

```bash
cd /opt/conduit/src
sudo git pull
sudo docker build -t conduit-web:local frontend
sudo systemctl disable --now conduit-web
sudo docker run -d --name conduit-web \
  --network host \
  --env-file /etc/conduit/web.env \
  --restart unless-stopped \
  conduit-web:local
sudo docker ps
```

Checkpoint: look at the `STATUS` of `conduit-web`. It says `Restarting`. Your site is down.

**4. Read the logs before you guess:**

```bash
sudo docker logs conduit-web
```

Checkpoint: `Cannot find package 'dotenv'`.

> [!NOTE]
> `dotenv` is listed under `devDependencies`, the packages needed only while developing. In Lesson 4 `npm install` installed everything, so nobody noticed. The box installs only what the running program declares (`npm ci --omit=dev`). The bug was always there; the box made it visible. That is one more thing a box is good for.

**5. Fix the declaration.** On the laptop, in `frontend/package.json`, move the line `"dotenv": …` from `devDependencies` to `dependencies`. Then update the lock file and push:

```bash
docker run --rm -v "$PWD/frontend:/app" -w /app node:22-slim npm install --package-lock-only
git add frontend/package.json frontend/package-lock.json
git commit -m "dotenv is needed at run time"
git push
```

**6. Rebuild and start again** on the server:

```bash
cd /opt/conduit/src
sudo git pull
sudo docker build -t conduit-web:local frontend
sudo docker rm -f conduit-web
sudo docker run -d --name conduit-web \
  --network host \
  --env-file /etc/conduit/web.env \
  --restart unless-stopped \
  conduit-web:local
```

Checkpoint: `sudo docker ps` shows both containers `Up`, and `https://YOUR-NAME` works. Sign in and open an article.

## Mission 4 · The robot builds the boxes (25 minutes)

**1. Teach the robot to build and publish both images**, and pause the deploy job while the server is being moved. In `.github/workflows/ci.yml`, add this job before `deploy`, at the same indentation as `unit-tests`:

```yaml
  build-images:
    needs: [unit-tests, secret-scan]
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v7
      - name: Name the images
        run: echo "REGISTRY=ghcr.io/${GITHUB_REPOSITORY_OWNER,,}" >> "$GITHUB_ENV"
      - name: Log in to the registry
        run: echo "$TOKEN" | docker login ghcr.io -u "$GITHUB_ACTOR" --password-stdin
        env:
          TOKEN: ${{ secrets.GITHUB_TOKEN }}
      - name: Build the API image
        run: >
          docker build backend
          --tag "$REGISTRY/conduit-api:$GITHUB_SHA"
          --build-arg APP_REVISION="$GITHUB_SHA"
          --label org.opencontainers.image.source="https://github.com/$GITHUB_REPOSITORY"
      - name: Build the frontend image
        run: >
          docker build frontend
          --tag "$REGISTRY/conduit-web:$GITHUB_SHA"
          --label org.opencontainers.image.source="https://github.com/$GITHUB_REPOSITORY"
      - name: Deliver both images
        run: |
          docker push "$REGISTRY/conduit-api:$GITHUB_SHA"
          docker push "$REGISTRY/conduit-web:$GITHUB_SHA"
```

Then change the two lines at the top of the `deploy` job to:

```yaml
  deploy:
    needs: [unit-tests, secret-scan]
    # Paused while the server moves to containers (Lesson 7). Lesson 8 turns it back on.
    if: false
```

> [!NOTE]
> The playbook from Lesson 5 still installs the application the old way and starts the hand-made services. Run now, it would fight with the containers for the same ports. Changing how a server runs is a migration, and during a migration the old automation waits.

Read the new job with the instructor:

- `GITHUB_REPOSITORY_OWNER,,` turns your username into lower case: registry names must be lower case.
- `permissions: packages: write` lets this job, and only this job, publish images.
- Each image is tagged with `$GITHUB_SHA`. Nothing is ever overwritten.

**2. Commit, push, open a pull request into your own fork, merge it:**

```bash
git add .github/workflows/ci.yml
git commit -m "Build and publish both images for every commit on main"
git push
```

On `main` the job `build-images` runs after the two checks and takes one or two minutes.

**3. Check that the images are public.** Open your GitHub profile → **Packages** and open `conduit-api`. If it says **Private**, open **Package settings → Change visibility → Public** and confirm with the package name. Do the same for `conduit-web`.

> [!NOTE]
> Anybody can now download your images. Look at what is inside: the code, which is already public on GitHub, and the libraries. The secrets are not in the image; they stay in `/etc/conduit` on the server and are handed to the container when it starts. Whatever you would not publish must never be built into an image.

## Mission 5 · Seconds, not minutes (20 minutes)

**1. Run the robot's images.** On the laptop:

```bash
git switch main
git pull
git rev-parse HEAD
```

On the server, with that SHA and your username in lower case:

```bash
SHA=<the SHA>
sudo docker pull ghcr.io/<you>/conduit-api:$SHA
sudo docker pull ghcr.io/<you>/conduit-web:$SHA
sudo docker rm -f conduit-api conduit-web
sudo docker run -d --name conduit-api --network host --env-file /etc/conduit/conduit.env \
  -e UVICORN_HOST=127.0.0.1 --restart unless-stopped ghcr.io/<you>/conduit-api:$SHA
sudo docker run -d --name conduit-web --network host --env-file /etc/conduit/web.env \
  --restart unless-stopped ghcr.io/<you>/conduit-web:$SHA
curl -s localhost:8000/api/health-check
```

Checkpoint: the `revision` is the SHA. The server never saw `pip` or `npm`.

**2. Go back to the image you built by hand,** and time it:

```bash
time ( sudo docker rm -f conduit-api && sudo docker run -d --name conduit-api --network host \
  --env-file /etc/conduit/conduit.env -e UVICORN_HOST=127.0.0.1 --restart unless-stopped conduit-api:local )
curl -s localhost:8000/api/health-check
```

Checkpoint: `time` shows less than a second, and a few seconds later the health check answers `"revision":"local"`. Write the time on the board next to last week's rollback.

**3. Go forward again** with the same command and the robot's image `ghcr.io/<you>/conduit-api:$SHA`.

> [!NOTE]
> Nothing was downloaded, installed or built. Both images were already on the server, complete. A rollback became “stop one box, start another”. That is the main thing containers changed for releases.

## Troubleshooting

1. **`permission denied while trying to connect to the Docker daemon`.** You forgot `sudo`.
2. **`docker build` fails at `COPY package-lock.json`.** The lock file is not on the server yet: commit it on the laptop, push, and `sudo git pull` on the server.
3. **`npm ci` fails with `package.json and package-lock.json are not in sync`.** You changed `package.json` but not the lock file. Run the lock-file command from Mission 3 again.
4. **`address already in use` when a container starts.** The old service still runs. `sudo systemctl disable --now conduit` (or `conduit-web`), then start the container again.
5. **A container shows `Restarting`.** Read `sudo docker logs <name>`. Fix the cause, then `sudo docker rm -f <name>` and start it again.
6. **`denied` or `unauthorized` on `docker pull`.** The package is private (Mission 4, step 3), or the username in the image name has capital letters.
7. **`manifest unknown` on `docker pull`.** There is no image for that SHA yet. Wait for `build-images` to finish, and use the full SHA.
8. **The server stops answering, even over SSH, while an image builds.** It ran out of memory. Restart the VM in the Azure portal (**Restart**), then add the swap file from Mission 1 before you build again.
9. **The site shows `502 Bad Gateway`.** Caddy cannot reach the frontend. `sudo docker ps` and `sudo docker logs conduit-web`.

## Commands for today

| Goal | Command |
|---|---|
| Build an image | `sudo docker build -t <name>:<tag> <folder>` |
| Start a container | `sudo docker run -d --name <name> … <image>` |
| What runs? | `sudo docker ps` (add `-a` to see stopped ones) |
| Log of a container | `sudo docker logs <name>` |
| Run a command inside | `sudo docker exec <name> <command>` |
| Remove a container | `sudo docker rm -f <name>` |
| Download an image | `sudo docker pull <image>` |
| Images on this server | `sudo docker image ls` |
| Layers of an image | `sudo docker history <image>` |
